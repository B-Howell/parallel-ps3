# Changelog of the libretro core

What changed in the libretro core of this fork, newest first. Changes that come with a merge of upstream RPCS3 are in upstream's own history; a merge is noted here with the upstream build it brought in.

## Unreleased

- **A thread opening a dialog waits for it untimed.** Not yet run on a game.
  - The on-screen keyboard, the message dialog, the home menu, the friends, user and trophy lists and the receive and send message dialogs each woke every millisecond to see whether the dialog had been taken up or closed. They now wait untimed (`libretro_wait_on`) on the dialog's own word, woken by it or by any change of the emulator's state, a stop among them.
  - The receive and send message dialogs also look at `sceNpBasicAbortGui`'s flag, and the send dialog at the press asking for its confirmation. Both now wake the waiter (`libretro_event`) as they are set.
  - A check fails if a timed wait comes back anywhere in the overlays. This was tested against a mutant that puts one back. No test drives a dialog's waiting thread: it needs the renderer and the overlay input thread.

- **A dialog belongs to the renderer: its input and its news are handed over, with no lock.** Not yet run on a game; the friends list and message dialogs not yet run online.
  - **Input:** the overlay input thread called each dialog's button and key handlers itself, while the renderer drew the same dialog. So the on-screen keyboard, the home menu's tabs, the friends list and the receive and send message dialogs each held a mutex. Each press is now handed to the renderer on a lock-free stack (`user_interface::post_call`, an `mpsc_stack`). The renderer runs them, in order, just before it updates the dialog (`take_input`), so it alone touches the dialog's elements. Calls never taken up are dropped with the dialog.
  - **The game's calls and the server's news** go the same way: `cellOskDialog`'s clear, set-text, insert and close, the friend and message callbacks from RPCN, and the lists the dialogs open with.
  - **The on-screen keyboard's text** was a plain array the renderer wrote and the game's calls read. It is now published whole (`osk_text_t`, as the text served to the game already was) and read in place. A clear from the game publishes the empty text at once. The confirm check's result is turned back in the buffer already lent to it, not a second one.
  - **What a press chose** (the message picked, the friend to send to) is taken with the press, so the thread waiting on the dialog no longer reads the renderer's list.
  - **No blocking call on the renderer:** adding, removing or rejecting a friend is a round trip to the server, and is now a job on the NP thread. Before, the friends list also waited for the connection on the renderer as it redrew. It now waits once, as the dialog opens, and the renderer only looks at whether it is connected.
  - `std::lock_guard` count 14. A check fails if a lock comes back in any of these dialogs. `test_held_queues` hands calls over from two threads while a third takes them up: it fails on a mutant that runs them newest first, and on one that runs those left over as the dialog goes.

- **On-screen messages, dialog text and the home menu's icons take no lock.**
  - **Messages:** any thread queuing a message took the message overlay's mutex, and the renderer took it on every frame the messages were drawn. A message is now handed to the renderer on a lock-free stack (`mpsc_stack`). The renderer takes it up as it updates the overlay, dropping it there if the same message is already shown or queued, as before. The caller asks for a flip so it shows even when the game is not flipping.
  - **Dialog text:** the message dialog's text, its progress bars' text and the debug overlay's text were a string and a dirty flag under a `std::mutex`. They are now published whole and taken by exchange (`atomic_ptr`).
  - **The home menu's icons:** these were a map under a mutex. They are now one slot per icon, loaded once: the first to publish it by compare-and-swap wins, and a loser frees its own.
  - `std::lock_guard` count 32. A check fails if a lock comes back in any of these. `test_held_queues` drives the message overlay through its own code: a duplicate is now dropped as the renderer takes it up, and the test fails on a mutant that keeps it. The text and the icons have no test of their own. Not yet run on a game.
- **The overlays take no lock on the draw path.** The Vulkan and OpenGL presents took the overlay manager's mutex while they drew the overlays and freed the removed ones, so a dialog opened or closed on another thread could hold up a flip.
  - **The lists:** the overlays shown, and those taken off whose resources are yet to be freed, are now published whole. A change (add, remove, dispose) is made to a copy and published by compare-and-swap; it is made again from the newer lists if another change got in first. The lists it replaces go once no reader is in (`retro_retire`).
  - **The renderer** reads the lists as they were when its draw began (`display_manager::reader`) and never waits; a change is drawn from the next flip. The queue of removals deferred while the lock was taken is gone, as removing no longer waits either.
  - **The input thread** keeps its own stack of the dialogs it runs, rather than pushing the interrupted ones back on the shared queue under a mutex. Another thread's push can no longer get in between, and the order is as before.
  - **The performance overlay** is set up on the RSX thread, which draws it, so it no longer takes the manager's lock.
  - `std::lock_guard` count 38. A check fails if a lock comes back in the overlay manager or the presents. No new test: the publishing is the pattern the VFS and RPCN states use. Not yet run on a game.
- **The Windows build is whole again.** Two of the last patches broke it, unseen by the Linux build:
  - **The network thread:** its `windows_poll` call gave `::size32` a count rather than a container.
  - **The TUS manager:** its `std::mutex` lost the header that brought in `<mutex>`. The mutex was never taken, so it is gone rather than included for.
  - Both files are now built with MinGW (`x86_64-w64-mingw32-g++ -fsyntax-only`) before a patch goes out. Not yet built on Windows here.
- **The signaling handler takes no lock.**
  - **The handler's state:** its one mutex, over the peers, the queued packets and the contexts, was taken by 19 calls and by its thread's whole round. All of it now belongs to its thread, and calls are handed over (`on_thread`, on `owner_calls`, whose waker wakes the thread's timed wait).
  - **Asking RPCN for a peer's details:** `init_sig1` now does this from its caller's thread, not from the signaling thread. The NP thread may itself be waiting on the signaling thread, so the two never wait on each other.
  - **Retransmit timing:** the signaling protocol's retransmits stay on the host's clock. The peers on the other end of the network keep real time.
  - `std::lock_guard` count 45. A check fails if a lock comes back. No new test: only a game online drives it. Not yet run online.
- **The NP handler takes no lock.**
  - **The handler's state:** it had 14 mutexes, over the requests pending, the Matching2 results, the basic events and their handler, the messages selected, the players' history, the GUI's requests, notifications and result, the quick matches and the custom menu. All of it now belongs to the NP handler's thread, and each change is handed there (`on_np_thread`, on `owner_calls`).
  - **The NP handler's thread** now runs with RPCN or without: it returned at once before when RPCN was off. It wakes on a call handed over as well as on the client's packets and the emulator's state.
  - **`sceNpInit` and `sceNpTerm`:** these take turns by a compare-and-swap. One made while the other is under way returns as if that one came first.
  - **The Matching2 set-up and take-down** flip their flag by test-and-set. The `sceNp2` checks of a single flag drop their lock.
  - **The signaling callbacks:** a signaling context's extended handler and a Matching2 context's signaling callback are now one word each with their argument (`sysutil_cb_word`). The signaling thread reads them whole; it read the Matching2 one with no lock before, too.
  - **Unused mutexes gone:** those in the TUS, score and Matching2 contexts were never taken.
  - **Save states:** they keep the bytes of the basic handler, a word in place of its mutex.
  - `std::lock_guard` count 62. A check fails if a lock comes back in any of these. No new test: the hand-over is `owner_calls`', which `test_owner_calls` covers, and only a game online drives the rest. Not yet run online.
- **Socket data is sent and received in place.**
  - **Receiving:** `recvfrom` allocated a vector the size the game asked for, received into it, returned it by value, and then copied it into the game's buffer. Now it receives straight into the game's buffer: the native socket's `recvfrom`, the DNS hook, and the P2P and P2P stream queues all write there.
  - **Sending:** `sendto` copied the game's data into a vector first. Now it sends from the game's memory, which stays as it is while the game is in the call.
  - **P2P sends:** these copied the data again to put the vport header in front. Now the system gathers the header and the data into one datagram: `sendmsg` with two `iovec`s, or `WSASendTo` with two `WSABUF`s, in a new overload of `np::sendto_possibly_ipv6`.
  - **P2P stream packets coming in:** each was copied into a vector to be checked. It is now checked, with its checksum zeroed, in the port's own receive buffer.
  - **Bad buffers:** a buffer that is not all there gets `EFAULT` at the start, not partway through.
  - **No more spinning:** the P2P stream's send no longer spins on `EAGAIN`. A packet that wants an ack is sent again by the retransmitter when due; one that does not is dropped, as a datagram may be.
  - **Lock parameters gone:** the socket calls drop their `is_lock` parameter, which nothing locks any more.
  - A check fails if a vector in between, or the spin, comes back. No test drives the calls: only a game online does. Not yet run online.
- **sys_net takes no lock.** Before, each socket had its own mutex, the P2P port list and each port's vports had theirs, the threads to wake had one, and each network thread had one for its loop. That came to 61 `std::lock_guard`s and the rest.
  - **One owner:** all of it now belongs to the network thread, and it alone touches any of it. A syscall, the RPCN and signaling threads, and the P2P stream retransmitter hand what they need done over to it (`net_call`, on `owner_calls`) and wait.
  - **Waking the network thread:** handing a call over pokes its wake-up socket. To make that possible, `owner_calls` gains a waker (`owner_calls_set_waker`), called with every wake, for an owner that waits on something other than its wake word.
  - **The P2P thread:** its polling is folded into the network thread. One untimed `poll()` covers the native sockets, the P2P ports and the wake-up.
  - **A call that blocks** (`accept`, `connect`, `recvfrom`, `sendto`, `sendmsg`, `poll`, `select`) queues on the network thread, then sleeps once back on its own thread. If its wake comes first, the sleep is cancelled, as `sys_event_queue_receive` does.
  - **Closing a socket** runs between the network thread's rounds, so no copy of the socket is left in one. This replaces taking both threads' loop locks.
  - **The P2P retransmitter:** it spun on `EAGAIN` from a full send buffer. It now leaves the packet for its next due time.
  - `std::lock_guard` count 109. `test_owner_calls` gains an owner that waits on its own word, woken only by the waker: 2000 calls from two threads all run, and a mutant that never calls the waker hangs. The sys_net hand-over itself has no test of its own: only a game online drives it. A check fails if a lock comes back anywhere in sys_net. Not yet run online.
- **The network threads no longer poll on a timer.** The network thread called `poll()` with a 1 ms timeout and the P2P thread with a 1 ms one (5 ms on Windows), around and around, whenever anything was waited on. Both now wait in `poll()` untimed.
  - **The wake-up:** each thread's poll set includes a wake-up socket, from a new C89 module, `net_wake.c`. It is a UDP socket on the loopback, connected to itself.
    - It is poked when a socket is queued for polling or taken off, when a P2P port is made, and when the thread is to stop.
    - Pokes made before the thread reads them off are one datagram.
  - **Socket timeouts (`SO_RCVTIMEO`, `SO_SNDTIMEO`):** these were checked against the clock by the network thread on every 1 ms round. They are now the waiting PPU thread's own timed wait (`lv2_obj::wait_timeout`), as `poll` and `select` already were.
    - When the wait ends, the thread takes itself off the socket's queue.
    - If it was still on the queue, the call timed out.
    - If it was not, the network thread got to it first and its result stands.
  - **Windows:** with no socket to poll, `windows_poll` slept for the timeout; it no longer sleeps. A connect that fails silently, which `WSAPoll` did not report before Windows 10 2004, is now noticed at the thread's next wake-up rather than within 1 ms.
  - The locks in sys_net are not touched here.
  - `test_net_wake` checks that a poke wakes a thread blocked in `poll`, that pokes before a drain are one datagram, and that a poke after it wakes it again. It fails on a mutant that never sends, and on one that never clears. A check fails if a timed poll or sleep comes back in the network threads, or a clock check in the socket calls. Not yet run online.
- **Trophies take no lock and no clock.**
  - **The manager:** every sceNpTrophy call took its `shared_mutex`, which kept a context alive while the call looked at it. The manager and its contexts now belong to the HLE thread, and each call looks at them there (`hle_call`). Unlocking a trophy reads the clock on the PPU thread first, since the HLE thread has no guest stack.
  - **Registering a context:** this runs in three parts on the HLE thread: before the game's callback, after it, and after the sync with the RPCN server. Neither the game nor the network is waited on in any of them.
  - **Registering's pacing:** it took at least 2 seconds by the wall clock, and sent each event after a 50 ms timeout if the game had not taken it. Now each event goes once the game has taken the one before (`cellSysutilCheckCallback`). If the game has not taken it within a few `retro_run` frames, the rest go anyway. There is no minimum time.
  - **The home menu's trophy name:** this was a string under a mutex. It is now published whole (`atomic_ptr`), and the menu holds the published string rather than copying it.
  - `std::lock_guard` count 170. A check fails if a lock or the clock comes back. No new test: only a game with trophies drives it. Not yet run on a game.
- Four more places take no lock:
  - **The PPU JIT's modules:** 256 maps, each under a mutex, now belong to the HLE thread, and a module is added and removed there (`hle_call`). The entries stay in place, so a caller keeps its own entry. A removed module is still destroyed on the caller's thread.
  - **The shared memory area (`sys_mmapper_get_shared_memory_area`):** it was made once, under a mutex. Now the first caller to finish publishes it with a compare-and-swap. A caller that loses gives its own area back and uses the winner's.
  - **sys_ss's allocations:** these were an `unordered_set` under a mutex, which allocated as it grew. Now they are one bit per 64 KiB page of main memory, set when given out and cleared when given back. Only one caller can clear a bit, and nothing is allocated.
  - **The AV chat callbacks (cellSysutilAvc, cellSysutilAvc2):** each callback and its argument were two fields under a mutex. They are now one 64-bit word, set if none is there by compare-and-swap. Save states keep the format they had.
  - `std::lock_guard` count 172. A check fails if a lock comes back in any of these. No new test: each is one word or the HLE thread's hand-over, which `test_hle_service` covers, and only a game drives them. Not yet run on a game.
- Three more places take no lock:
  - **sys_usbd's event waiters:** the events already belonged to the USB thread, but the threads waiting for one were a list under a mutex. Now that list belongs to the USB thread too, and taking an event or joining the waiters is done there (`on_thread`).
    - A waiter given its event before it has gone to sleep has that sleep cancelled, as `sys_event_queue_receive` does.
    - A thread stopping asks the USB thread whether it is still waiting.
  - **The PPU linkage tables:** these are the exports and imports made as a module loads or unloads, plus the library locks and the PRX names. They took two mutexes and a third for the names. They now belong to the HLE thread, and every change to them is made there (`hle_call`). Looking an export up already took no lock.
  - **The PNG encoder:** it kept a copy of its config and resources under a mutex, to check a picture against three limits. The limits are now one 64-bit word; the resources it never read are gone.
  - `std::lock_guard` count 183. A check fails if a lock comes back in any of these. No new test: they use the USB and HLE threads' hand-over (`owner_calls`), which `test_owner_calls` and `test_hle_service` already cover, and only a game drives the paths here. Not yet run on a game.
- **The on-screen keyboard's text takes no lock.** The text cellOskDialog serves to the game was a buffer under a `shared_mutex`, taken by eight calls; three of them did not touch the text at all, and one held it while waiting for the game's force-finish callback.
  - The text now lives in a new C89 module, `osk_text.c`. Each set writes a whole text into a node from a fixed pool of eight and publishes it by swapping a pointer.
  - The node it replaces goes back to the pool once no reader is in (`retro_retire`). Getting the text copies it from the published node straight into the game's buffer, so a reader never sees half of one text and half of another.
  - A set waits for a free node only if readers are holding back every retired one, and is woken as they leave. Nothing is allocated.
  - `test_osk_text` (also under ThreadSanitizer) has two threads setting texts 100000 times while two read them. It fails on a mutant that writes into the published node. A check fails if a lock comes back in cellOskDialog. `std::lock_guard` count 192. The overlay keyboard's preview lock is not touched here. Not yet run on a game.
- Guest page faults take no lock and no clock:
  - **The areas watched for faults** (`sys_mmapper_enable_page_fault_notification`) were a vector under a mutex, searched on every fault. They are now 16 slots, one per 256 MB, since such an area starts on that bound. Enabling takes a slot by compare-and-swap, freeing the area clears it, and a fault reads its slot with no search. Save states keep the format they had.
  - **The threads waiting out a fault** were a map under a mutex. Each thread is now marked in its own word, set before the event goes so that the game's recovery finds it. A recovery takes the mark by compare-and-swap, so only one wins. Freeing an area looks at the threads' marks only while some thread is faulted.
  - **A full event queue:** the faulting thread tried again every millisecond. It now waits for the game to take an event from the queue, or for the queue to go away, the port to be disconnected or the thread to stop, as the RSX's event sends already do.
  - `std::lock_guard` count 200. A check fails if the lock or the clock comes back. No test drives it: a fault needs a guest page fault on a watched area, which only a game sets up. Not yet run on a game.
- Four more places take no lock:
  - **The VFS:** mounting and unmounting were one at a time under a mutex. Each now publishes its changed copy of the tree with a compare-and-swap; one that loses to another is made again from the newer tree. The trees replaced are kept on a lock-free stack (`mpsc_stack`) until the manager goes. Lookups already took no lock.
  - **A PRX's exports:** loading and unloading them took the module's mutex, and unloading the module took it to wait out either. The module's state, won by compare-and-swap, already lets only one thread at them; unloading the module now waits on a busy count, woken as the last thread leaves.
  - **The Gem (Move) positions:** these took a mutex for two floats. They are now one 64-bit word each, read and written whole.
  - **The audio backend's callbacks:** a `std::timed_mutex` and a `shared_mutex` guarded callbacks only the setting thread touches: the Null backend never calls them and the libretro one keeps its own, taken with no lock.
  - `std::lock_guard` count 203. `test_vfs_positional` and `test_audio_frontend` cover the VFS and the audio backend. A check fails if a lock comes back in any of these. Not yet run on a game.
- The PPU's far jumps (the branches patches and HLE redirect, taken on every call through one) take no lock. Every far jump took the jump table's `shared_mutex` as a reader, and adding or removing one (a patch applied, a module loaded or unloaded) took it as the writer. The table is now one published state: read with no lock under `retro_retire`, and replaced whole by a change (copy, change, compare-and-swap), the old one freed once no reader is in it. Its range, which every jump checks first, is a word read with no entry at all. A jump's mini-function is made before the jump is published with it. The expected TOCs checked with `ppu_debug` (`ppu_check_toc`, a reader lock on each check) are a published map the same way, and a module's are published before their checks are put in. `std::lock_guard` count 211. No CI test: the jumps need guest code and memory. A check fails if a lock comes back on the jump or the TOC check. Not yet run on a game.
- Score and TUS transactions (`sceNpScore*`, `sceNpTus*` online leaderboards and storage) take no lock and start no thread. Each transaction had a mutex and two condition variables, an asynchronous one started a `std::thread` of its own just to wait out its timeout, and the transactions in flight were a map under another mutex:
  - **Registration:** a request is now registered before it is sent, in slots claimed with compare-and-swap (`rpcn_reply_slots.c`). Before, it was registered after it was sent, so a reply faster than the registration found nothing.
  - **Finishing:** it is finished once, by the first to claim it of its reply, an abort or its timeout (`claim`, `finish`); the others are told no.
  - **Timeouts:** whoever looks after the deadline sees the timeout: the status asked, the wait, or the reply itself. A synchronous call waits on the transaction's state, woken as it finishes or at its deadline.
  - **Multi-part reads:** a requester changing the output buffers of a transaction still in flight (`get_score_data`, `tus_get_data`) has the change made on the NP handler's thread, where the reply's handler runs. No lock is needed between them.
  - **Tests:** `test_emu_waits` now has two threads claim each of 20000 transactions at the same moment and checks one wins each; it fails with the claim as a load and a store. It also checks a waiter woken by the reply, and a timeout seen by the wait and by the status. `std::lock_guard` count 215.
  - A check fails if a lock, a condition variable or a thread per request comes back. Not yet run online.
- The RPCN client is reached with no lock:
  - **The NP handler's reference to it:** this was a `std::shared_ptr` under `mutex_rpcn`, and the lock was held across the whole connection and login, so the handler's thread and every presence or trophy call waited on the network. About half the uses (every `get_rpcn()` in the requests) did not take the lock at all, against a reset on another thread. The reference is now published with no lock: a thread takes its own copy under `retro_retire`, and replacing or dropping it lets the old copy go once no reader is in it.
  - **The one client (`rpcn_client::get_instance`):** this was a `weak_ptr` under `inst_mutex`. It is now published the same way. Making a client is claimed with compare-and-swap; a thread that finds it claimed waits for the one being made, then takes that.
  - `std::lock_guard` count 242. No CI test: it needs the RPCN server. A check fails if `mutex_rpcn` or `inst_mutex` comes back. Not yet run online.
- The RPCN client's friends, messages and connection take no lock:
  - **Friends:** the friend list and its callbacks were under one `shared_mutex`, held even while the callbacks ran. They are now one published state, read by any thread with no lock and replaced whole by a change (copy, change, compare-and-swap). The old state is freed once no reader is in it (`retro_retire`, libretro-common). A callback registered with a read of the list still sees every change after it and none before. Notifications now call the callbacks after the change is published, so a callback that reads the list sees it.
  - **Messages:** these were under a `shared_mutex` (the messages, the new and active lists, and the message callbacks), and are now one published state the same way. The message counter is atomic.
  - **Connecting and logging in:** waiting for a connection or a login took a mutex the RPCN thread held for the whole attempt, then a semaphore given once. A second thread waiting at the same time could wait for good. Each is now a generation word moved by every attempt, and all its waiters are woken.
  - `std::lock_guard` count 253. No CI test: it needs the RPCN server. A check fails if one of these locks comes back. Not yet run online. The client's instance lock (`inst_mutex`) and the NP handler's locks are next.
- The RPCN client's queues take no lock. What the reader thread takes in for others was kept under four `shared_mutex`es:
  - **Notifications, replies and presence updates:** these go to the NP handler's thread, which takes each list whole. They are now pushed as nodes onto `mpsc_stack`s and taken oldest first. Presence updates still end with the last one for each user winning, as they did in the map. Taking the full presence states drops the updates so far, as before.
  - **Synchronous replies:** each goes to the one thread waiting for its id (login, friends, messages and the rest). They were a `std::map` under a lock. They are now 64 slots: the reader claims one with compare-and-swap and publishes it under the reply's id, and the waiting thread takes it the same way (`rpcn_reply_slots.c`, new, C89). The connection ending drops what no thread is waiting for any more, where the map kept it.
  - `std::lock_guard` count 275. `test_rpcn_reply_slots` (also under ThreadSanitizer, which found the slot's id read racing a new publication until it was made atomic) has one reader publish 20000 replies to four threads each waiting for its own ids. It fails if a slot is taken without matching its id. A check fails if a queue lock comes back. Not yet run online.
- The RPCN client and the NP handler's thread no longer poll. Waiting for a synchronous reply (`get_reply`: login, friends, messages, presence and the rest) and for the server's protocol version as it connects slept 5 ms at a time. The NP handler's thread, with nothing to hand on, slept 200 ms between looks ("TODO: replace with an appropriate semaphore"). The client now has an event word (`rpcn_client::m_events`), moved by every packet its reader takes in and by the connection ending or the client going away. The two waits wait on it, and the handler's thread waits on it as well as on `g_libretro_events` (the emulator's state, a client made or let go) and on being told to end. A reply or notification now reaches the game as it arrives, where it took up to 200 ms. No CI test: it needs the RPCN server. A check fails if a poll comes back in either. Not yet run online. The RPCN client's and NP handler's own locks (63 between them) are still there; they are the next patch.
- The recording encoder, the TAR extractor and the package install no longer sleep or poll:
  - **Recording encoder (`video_encoder`):** with nothing to take it slept 1 µs at a time, effectively spinning, or 10 ms while paused. It now waits on the sink's filled word, which moves with every frame or audio block handed over and with a pause, flush or stop asked (`wake_consumer`). It is also woken as its thread is told to end. A pause or stop that asked for a flush slept 1 µs or 1 ms at a time until the encoder had flushed; it now waits on the freed word, which the encoder moves as it finishes the flush or ends.
  - **TAR extraction:** the archive reader, with every buffer full, polled every 1 ms for room, and the file writer yielded in a loop for the next chunk. Each now waits on the other's count, which is notified as it moves.
  - **Package install (`install_pkg`):** it slept 5 ms at a time to log the progress while the installer ran. It now joins the installer, which waits.
  - **Tests:** `test_video_sink` (also under ThreadSanitizer) covers the sink's waits. A check fails if a sleep, a poll or a yield comes back in these three. Not yet run on a game.
  - `cellRec`'s own recording thread still wakes every microsecond, pending a decision on how it should catch up on audio blocks. The RPCN client's 5 ms polls go with its own patch.
- The renderer no longer spins while waiting for the GPU or another thread:
  - **Vulkan fences:** a wait with no time limit (`vk::wait_for_fence`, used by every command buffer's `wait()` and so by `begin()`, `wait_all()` and the resize sync) spun on `vkGetFenceStatus`. It now blocks in `vkWaitForFences`, which the driver wakes as the GPU signals. Waiting for the offloader to submit (`fence::wait_flush`) spun on its flag; it now waits on it, and the submit notifies it.
  - **Occlusion query results:** a ZCULL read that needed its result spun on `vkGetQueryPoolResults`. After the first non-waiting look (which can still answer early if a sample passed), it now asks once with `VK_QUERY_RESULT_WAIT_BIT`, so the driver blocks until the result is there.
  - **Host GPU labels:** draining the label queue (`RSXDMAWriter::drain_label_queue`) spun on the counter the GPU writes. Vulkan now waits for the submitted command buffers' fences instead. OpenGL still polls, as it has no such wait yet.

- lv2 event queues take no turn and do not spin (`lv2_evq.c`, new, C89). - Semaphores take no lock (4 `std::lock_guard`, and the semaphore's `shared_mutex`). This is the first of the kernel's sync objects done the per-object way. A new primitive, `turn_calls` (`Emu/CPU/turn_calls.c`, C89), gives an object its turn with no lock and no thread of its own. A thread that finds the object free runs its call at once, then the calls others handed it meanwhile, in order, and gives the object up. A thread that finds it taken hands its call over and sleeps on its own record until it has run. Free, as an object mostly is, that costs one compare-and-swap and one exchange, as a lock would; nothing spins and nothing is allocated. A semaphore's queue of waiters, and its count going below zero with them, now change in the semaphore's turn. A waiter queues itself there, then goes to sleep on its own thread, after its turn, since going to sleep is the one scheduler step that belongs to the sleeping thread; a post that wakes it in between cancels that sleep, as sys_mutex already has it. A post takes its waiters off the queue and wakes them in its turn, so a waiter whose timeout comes is never left between the two. A new test has four threads make 50000 calls each on one object: every call runs once, never two at once, and each thread's in order. Hooks in the test build widen the two windows where a call could be missed; the test hangs on either mutant (reported as a stall, not a failure). CI checks sys_semaphore has no lock. Unverified in games.

- Vulkan, "Async with Interpreter" and "Interpreter only" shader modes: the interpreter's pipelines now take their fixed-function state as dynamic where the device can (`VK_EXT_extended_dynamic_state` 1 to 3, which current NVIDIA, AMD and Mesa drivers have). - Vulkan, "Async with Interpreter" shader mode: less work per draw. This is the mode that draws with the shader interpreter, instead of skipping the draw, while a shader is still compiling, so elements don't flash black on a cold shader cache. It is still not the default. In this mode draws go back and forth between compiled shaders and the interpreter, and every interpreted draw used to copy the vertex and fragment programs into the interpreter's instruction buffers again (up to 8 KiB and more), whether they had changed or not. Now only what changed goes in: the program changes seen by every draw, the compiled ones included, are gathered, along with the program's few words of state and the buffer it is in (`vk_interpreter_uploads.c`). Each switch between the interpreter and a compiled shader also copied all 468 transform constants (7.5 KiB) again. The whole set last put on the ring is now taken as it is while no constant was written (a count the RSX moves on with each write) and no frame's ring space was given back. This also helps compiled shaders that read the constants by index, which took the whole set again with each new vertex program. A new C89 test checks that a change taken up by a compiled draw still reaches the next interpreted one, and when the constants can be reused. Unverified on real hardware.

- Only the renderer enters the texture cache now (Vulkan and OpenGL). A thread that faulted on memory the cache has locked, and could not deal with it alone (the change below), went into the cache itself, under the cache's lock and beside the renderer: it searched the cache, marked sections, and for memory that had to be written back first then asked the renderer to stop and did the flush on a second command buffer. It now hands the fault to the renderer and waits: it posts a record from its own stack with one compare-and-swap (`Emu/RSX/Common/guest_faults.c`, C89), and the renderer, at the points where it already looked for flush requests, handles the fault exactly as it handles one of its own and wakes the thread. Whether a fault is the cache's at all is read from the table of locked pages, with no lock, so faults that are somebody else's never go near the renderer. A renderer that another thread has paused still answers, since the thread that paused it may be the one waiting; one that is waiting for the offloader thread is told the offloader's range, as before, but before the offloader touches the cache rather than after. When the renderer ends it answers what is waiting and closes, and a fault after that is handled the old way. The cache's lock is still in the code but no two threads meet on it any more; taking it out is the next step. For the faults that needed a flush nothing is slower - they waited for the renderer before; the few that did not now wait for it to reach its next check. CI has four threads posting faults while a fifth answers and then closes under them: every fault gets its own answer, each thread's in order, and no thread is left waiting; a close that forgets a waiting fault, an answer that wakes nobody, or a post after the close each hang or fail the test. Not tried with a game yet.
- A game thread that writes over a texture no longer takes the texture cache's lock (Vulkan). The renderer write-protects the guest memory its textures were read from, and a game writing there faults: the faulting thread took the cache's lock, searched it, and waited for the renderer whenever it held the lock, which it does for as long as it uploads. For the common case - the page holds only textures the renderer read from, nothing it has to write back - the thread now makes the page writable itself, leaves a note and goes on; the renderer throws the stale textures away when it next enters the cache. A table with one word per 4 KiB page says how each page is protected (`Emu/RSX/Common/guest_page_locks.c`, C89). The two sides cannot undo each other: a lock is counted in the table before its protection is applied; a thread takes the page in hand with one compare-and-swap, which fails if anything on it needs flushing or the occlusion-query code holds it; and whoever protects a page waits for a thread that has it in hand, a few instructions. The thread also no longer takes the sampler lock, which the renderer holds while it loads a draw's textures; it sets a flag the renderer takes there. Still the old way: pages with something to flush, reads, the renderer's own faults, and hosts whose pages are larger than 4 KiB; the cache's lock itself is still there for those, and going without it is the next step. CI runs a model of the two sides - a renderer locking, unlocking and collecting notes on six pages against three threads writing to them - and checks that no page is ever writable while a lock on it is in force with no note left, also under ThreadSanitizer; without the wait, or with a thread that ignores a page it must not take, the test fails. Not tried with a game yet.
- Resolving a PS3 path to a host path takes no lock. Every open, stat and directory listing a game makes looked the path up in the mount table under a reader lock that all threads shared. The table is now a tree that is never changed once it is in use: mounting and unmounting, which happen at boot and when a device comes or goes, copy it, change the copy and swap it in, and a lookup walks whichever tree was current when it started. Replaced trees are kept until the emulator stops (a few dozen small ones over a session), so a lookup never walks freed memory. CI has three threads resolving paths while another mounts and unmounts a device two thousand times: a path on a mount that stays always resolves to the same place, and a path on the one that comes and goes only ever to one of its two right answers; changing the tree in place instead crashes the test every run. One thread alone is neither faster nor slower (about 250 ns either way - the time goes into building the strings, not the lock); the gain is that threads no longer share a lock here. Not tried with a game yet.

- Fixed, from the thread change two entries below, before any release had it: a thread that exits settles who joins it and wakes that thread while holding the lock over all IDs, which used to keep a join on it from being half done at that moment. Once joins stopped taking that lock, an exit could wake a joiner that had named itself but not yet gone to sleep, and the joiner then slept with nobody left to wake it. The exiting thread now lets the calls that are inside on its ID finish, and keeps others out, for as long as it held the lock against them (idm::close).

This removes two of the shared locks that were left. Not tried with a game yet.
- Sockets, threads and memory no longer take the lock over all kernel object IDs for their per-object calls: the thirteen sys_net calls that work on one socket (accept, bind, connect, the get and set calls, listen, recvfrom, sendto, sendmsg, shutdown), joining, detaching, renaming, starting a thread and reading or setting its priority, mapping and unmapping shared memory, memory containers, sys_vm's two block calls and the SPU thread lookup count themselves in on their own object instead (idm::check_entered, idm::get_entered), as event ports do since the change below. poll and select, which look at many sockets at once, and the calls that walk every object of a kind still take the lock. Not tried with a game yet.
- Event ports, event queues and timers no longer take the lock over all kernel object IDs. sys_event_port_send is the call behind most wake-ups in a game - audio, pad, vblank, timers and thread joins all end in it - and every send took the reader lock that every other kernel call also takes. It now counts itself in on the port's own word and out again: two interlocked steps, as the lock took, on a word no other object shares. That one count keeps the port alive and its queue connected, so nothing is pinned and no reference is counted; connecting and disconnecting a port, which change the queue the send reads, let the sends that are in there finish first (idm::close), and every way of removing an ID now does the same. One thread, measured in CI: 19.8 ns under the reader lock, 16.5 ns counted in; and for a lookup that keeps the object (receive from a queue, wait on a condition) 51 ns under the lock, 28 ns counted in (42 ns before this change). sys_event_queue_receive, _tryreceive and _drain and the five timer calls are converted the same way. CI has four threads reading ports' queues while another connects, disconnects, removes and recreates them: no thread is inside when the queue changes or once the port is gone; with either wait taken out, the test fails every run. Not tried with a game yet.
- Lightweight condition variables no longer take the lock over all kernel object IDs: _sys_lwcond_queue_wait, _signal and _signal_all find the lwcond with no lock. These calls name a second object, the lwmutex, and signal can name a thread: both were used through bare pointers that only the lock over all IDs kept alive, and are kept with references now. A wait counts the thread among the lwmutex's waiters and a signal can move a woken thread into the lwmutex's queue - what a destroy of the lwmutex asks about - so the lwmutex is counted in on as well (idm::enter), and always before any object's own lock is taken, so that a thread waiting for a destroy to decide never holds a lock that a thread the destroy waits for needs. CI has four threads counting themselves in on a lwcond and a lwmutex at once while another destroys and recreates both kinds in turn: neither destroy succeeds on an object with such a waiter, and the test ends, which is the check that nobody waits on anybody. Not tried with a game yet.
- Reader-writer locks no longer take the lock over all kernel object IDs: sys_rwlock_rlock, _tryrlock, _wlock and _trywlock, which take the lock or wait for it, count themselves in on the ID (idm::get_entered) so that a destroy sees them; _runlock and _wunlock only keep a reference. And the lock-free lookup that keeps the object is now faster than the locked one it replaces, not only free of the shared lock: with the object pinned, its reference is one increment, where loading the ID's pointer was three interlocked steps. One thread, measured in CI: 51 ns under the reader lock, 26 ns kept with a reference, 42 ns kept and counted in (before this change 49 and 64 ns). That speeds up the mutex, semaphore, event flag, lightweight mutex and condition variable paths of the changes below as well. Not tried with a game yet.
- Condition variables no longer take the lock over all kernel object IDs: sys_cond_wait, _signal, _signal_all and _signal_to find the condition with no lock. Signalling makes no thread wait on the condition, which is all sys_cond_destroy asks about, so it only keeps a reference; a thread that goes on to wait counts itself in on the ID first, as lightweight mutexes do, so a destroy waits those few instructions and finds it in the queue. Two helpers make the remaining kernel objects a one-line change each: idm::get_held and idm::get_entered do what idm::get did, without the lock, for code that makes no waiter and for code that may. sys_cond_create takes its mutex with the lookup that cannot return a new object for a destroyed ID. - Lightweight mutexes no longer take the lock over all kernel object IDs: _sys_lwmutex_lock, _trylock, _unlock and _unlock2 find the lwmutex with no lock. These are the calls behind every contended sys_lwmutex in a game. Taking a lwmutex that was just given up, and giving one up that nobody waits for, count no reference either. A thread that goes on to wait is kept safe from a destroy in a new way that leaves the waiting code exactly as it was, with nothing to undo: it counts itself in on the ID before it looks whether the ID still names the lwmutex (idm::enter), and a destroy that asks about waiters marks the ID, lets the threads that are counted in finish, and only then looks at the queue. Not tried with a game yet.
- Event flags no longer take the lock over all kernel object IDs: waiting on, trying, setting, clearing, cancelling and reading an event flag by its ID find it with no lock, as mutexes and semaphores do. Taking bits that are there, and setting bits that are set already, count no reference either. A thread that goes on to wait queues itself under the flag's own lock and then asks whether the ID still names the flag; sys_event_flag_destroy, which refuses while a thread waits, marks the ID before it looks at the queue - so either the destroy saw the thread and failed, or the thread leaves the queue again and reports that there is no such flag. sys_event_flag_set and _cancel took their reference with the lookup that could return a new object for a destroyed ID (see the semaphore change below); they use idm::hold now. Not tried with a game yet.
- Semaphores no longer take the lock over all kernel object IDs: waiting on, trying, posting to and reading a semaphore by its ID (sys_semaphore_wait, _trywait, _post, _get_value) find it with no lock, as locking a mutex does since the change below. Taking or adding a count that makes no waiter needs nothing more. A thread that goes on to wait makes itself a waiter under the semaphore's own lock and then asks whether the ID still names the semaphore; sys_semaphore_destroy, which refuses while there are waiters, marks the ID before it looks for them - so either the destroy saw the waiter and failed, or the thread is no waiter after all and reports that there is no such semaphore. Also fixed on the way, for mutexes too: a thread about to sleep took its counted reference with a lookup that reads an ID's key and then its object, and if the ID was destroyed and its place given to a new object between the two, the thread got the new object for an ID that no longer existed. The reference is now taken while the object is pinned (idm::hold). CI has four threads becoming waiters by ID while another destroys and recreates the semaphores: no destroy succeeds on a semaphore a thread has been told it waits on; without the second look, or with the old lookup, the test fails. Not tried with a game yet.

- Locking and unlocking a mutex no longer take the lock over all kernel object IDs. Every syscall that names a kernel object by ID - a mutex, a condition variable, an event queue, a semaphore - looked it up under one reader lock shared by all threads and all object types, so every PPU thread wrote to the same word on nearly every syscall. This is the start of doing without it, module by module; `sys_mutex_lock`, `sys_mutex_trylock` and `sys_mutex_unlock` are the first. A thread now finds the object by announcing it in a hazard cell of its own (`idm::pin`, `Utilities/lf_hazard.c`, C89): no lock, no reference counted, and whoever removes an ID waits until no cell holds its object before the object can be freed. What the lock also guaranteed - that a mutex cannot be destroyed between being found and being locked - is kept by a mark `sys_mutex_destroy` puts on the ID while it checks that the mutex has no owner: a thread that has just become the owner asks whether the ID still names the mutex (`idm::still_named`), waits if a destroy is deciding, and if the ID is gone gives the mutex up and reports that there is no such mutex. Looking an ID up costs one thread 7.6 ns instead of 13.4, and threads no longer contend for it. The other kernel objects still use the reader lock. Covered by `test_lf_hazard`, `test_vfs_positional` (four threads locking mutexes by ID while a fifth destroys and recreates them) and a source check.
- Finding the buffer that mirrors a stretch of guest memory, and copying through it, take no lock (Vulkan). Texture uploads that go through the GPU ask for the DMA mapping of their source every time, and `map_dma` took the pool's mutex exclusively for each of them, mapped already or not; loads and flushes took it shared. Readers now look in a table with one entry per 64 KiB of guest memory (`Emu/RSX/Common/dma_views.c`, C89) that points at an unchanging description of the buffer: an existing mapping is found with one load and two compares, and a load or flush copies straight through it. Only making, growing or unmapping a mapping takes the mutex, and then brings the table up to date. A buffer that is replaced is handed to the deferred deletion with its description and still mapped, so a reader that found it a moment earlier can finish; buffers are also left mapped from the start rather than unmapped after the first fill and mapped again on first use. The two error messages for a transfer over unmapped memory are gone with the logging. Covered by `test_dma_views` (lookups, copies in both directions, ranges over two buffers, replacement under readers; also under ThreadSanitizer) and a source check.
- Mapping guest memory, and a fault the occlusion-query code is asked about, take no lock when there is nothing to do. Every memory map took a reader lock on the renderer's task mutex to see whether an unmap was still waiting to be handled - almost never - and every fault the texture cache did not take went on to the occlusion-query (ZCULL) code, which took a reader lock and searched a map for the page - almost never there. Each is now one load of a flag or a count kept beside the data, set under the same mutex as the data and before anything that could cause the notification or the fault; only when there is something to do is the mutex taken, exclusively. The renderer's own check of the pending unmap, which read a field of the range through `atomic_storage`, reads the same flag. Covered by a source check.
- What the Vulkan renderer is done with is disposed of and deleted with no lock. Every image, view, buffer or sampler the renderer lets go of is kept until the GPU has finished the commands that used it: disposing of one took a lock and appended to a vector in a list of scopes, and the driver thread, on every completed submission, took the same lock - shared, then upgraded - to cut the finished scopes out. Disposing is now a compare-and-swap push of a record onto a list; the driver thread takes the whole list in one exchange, puts it behind what it kept from last time and deletes what is due, in the order it was disposed of. Records come from and go back to a lock-free pool, so disposing of an object allocates nothing once the pool has filled (it grew a vector before), and a disposable carries a plain function pointer instead of a `std::function`. Holding the current event's objects for one more event (asynchronous texture streaming) is a mark on the event, which now also covers what is disposed of later in that event. Covered by `test_shader_corpus` (order, timing, a held event, and four threads disposing while a fifth completes events) and a source check.
- The Vulkan framebuffer cache is looked up with no lock. Every change of render target, and every overlay or post-process pass, looked its framebuffer up under a reader lock, in a hash map of vectors, comparing against each framebuffer's attachment views; a miss upgraded the lock. The cache is now a lock-free table (`Utilities/lf_sig_table.c`, C89) in memory of the core's own: a framebuffer is known by its size and by its attachments' images and formats, a copy of which the table holds, so a lookup is a walk of the slots' words that writes nothing and never touches a framebuffer another thread may be removing. Removing (unused for two frames, or made of an image that is going) marks a slot while it asks about it - the framebuffer is still found meanwhile - and empties it before the framebuffer is deleted; only two removals at once wait for each other. At most 1024 framebuffers are kept at a time (there was no limit). Measured against a stand-in for the old shape (not the old code itself), a lookup is 9 ns instead of 18 with 4 framebuffers, 17 instead of 18 with 16, and level at 64. The key's upper bits, which were left unset, are now defined. Covered by `test_lf_sig_table` (four threads adding, finding and sweeping their own while two look up everybody's, and one slot with two things taking turns in it; also under ThreadSanitizer) and a source check.
- The Vulkan texture cache's pool of spare images takes no lock. An image the GPU is done with is kept for reuse; putting one in took a lock, and every search for one - each time a texture or a temporary image is created - took a reader lock and then upgraded it, and walked the whole pool under it. The pool is now a lock-free one (`Utilities/lf_item_pool.c`, C89): a slot's key word is the image's key, a search is one plain load per slot - over about as many slots as there are images - and writes nothing until it finds a match, which it claims with a compare-and-swap; the count and memory total are added up when asked for, once a frame, instead of being kept on every put and take, and closing the pool on shutdown needs no lock either. Measured against a stand-in for the old shape (lock, upgrade, walk, erase - not the old code itself) a search that finds nothing costs 1 ns instead of 16 with the pool empty and 6 instead of 30 with 8 images in it, and taking an image and putting one back 31 ns instead of 45. Trimming the pool at the end of a frame still drops the older half. Covered by `test_lf_item_pool` (four threads putting and taking while a fifth trims, and closing the pool while threads put; also under ThreadSanitizer) and a source check.
- The Vulkan shader interpreter's caches are read and added to with no lock. Looking up the interpreter program for a draw took a reader lock whenever the draw's state differed from the last one's, as did finding the interpreter's two shaders, and the pipeline compiler's thread took the same lock to hand over each program it finished - so the renderer waited for it. The three caches are now lock-free maps: a program is made whole and then published with one exchange, and one that is replaced (an interpreter variant first served by a compatible program, then by its own) is kept until the interpreter is destroyed, so the program the renderer is drawing with never goes away under it and is held as a plain pointer rather than a counted one. A cache miss is no longer timed with the wall clock and logged. Covered by `test_shader_corpus` (six threads giving the same keys programs at once: none lost, none kept twice) and a source check in the library tests.
- Taking a Vulkan descriptor subpool takes no lock, and two threads can no longer take the same one. When a descriptor pool's current subpool is used up the next free one was looked for under a reader lock - and marked busy under that same shared lock, so two threads looking at once could both take it. A subpool is taken now by swapping its busy flag from 0 to 1 with a compare-and-swap and given back, once it has been reset, by storing 0; the subpools are a fixed array (256) with an atomic count, a new one put in a slot of its own. One reader lock and two exclusive ones gone. Not run on a GPU beyond the software driver the tests use.
- Polling a Vulkan command buffer takes no lock. `poke`, `wait` and `flush` of a command buffer chunk each took a reader lock - `poke` for every buffer of a chain whenever the next one is taken, and for the swap buffer every frame - to guard the one thing done when a submission is seen finished: the fence reset, the event completed, the buffer marked no longer pending. That is done once now by whichever thread claims it with a compare-and-swap, and a thread that comes meanwhile goes on without waiting; whether a buffer is pending is an atomic flag read with no lock. Three reader locks gone. Not run on a GPU beyond the software driver the tests use.
- The Vulkan memory totals are counters read with no lock. How much memory each memory type and each pool has in use - asked on every check of the memory load and, for the sampler count, on every trim - were maps behind a lock that each question took shared, and that counting a sampler in or out took exclusively. They are fixed arrays of atomic counters now (`VKResourceManager.cpp`): a question is a load, counting a sampler is one add, and three reader locks and two exclusive ones are gone. The record of what was allocated, which only allocating and freeing use, stays under its lock. Not run on a GPU beyond the software driver the tests use.
- The Vulkan render pass cache is read with no lock. `vk::get_renderpass` took a reader lock for every lookup that got past the one-entry cache in front of it; the passes are in the add-only lock-free map now (`Utilities/lf_u64_map.c`, key to handle), a lookup is a hash and a few loads, and two threads that miss the same key at once each make the pass and one is destroyed. The map gained `lf_u64_map_each`, for the destroy at shutdown. Not run on a GPU beyond the software driver the tests use.
- Finding the program for a draw takes no lock. Every draw that changes program looks up its vertex program, its fragment program and the pipeline of the two in the program cache, and each of the three lookups took a reader lock: two writes to a word the shader compiler threads share, and a wait whenever one of them was adding a program - on the render thread, in the middle of a frame. The three maps are `program_cache_map` now (`Program/ProgramStateCache.h`): buckets of chains, an entry pushed with a compare-and-swap and never moved, found with no lock; a pipeline's entry carries the pointer its readers load, null until whoever made the entry has linked it, which is what the placeholder under the lock was for. `test_shader_corpus` has six threads add the same 20000 keys in different orders: one entry a key, made by one thread, the same entry handed to all (fails without the look at what was pushed meanwhile). `reader_lock`, RPCS3's own name for the same kind of lock, is used 90 more times in the core; the render path's (texture cache, render pass and framebuffer caches, the shader interpreter) come next. Not run with a game or on a GPU.
- A game's file reads no longer go one at a time. `sys_fs_read` - the plain read, at the file's position, which is what most games load with - held its mount point's lock exclusively for the whole host read, so every read from the disc, or from the hard disk, by any thread and of any file, waited for the one before it. It holds no lock now: the read is counted on its file as a read at an offset is (`lv2_file::io_begin`), and the file's position is moved on with a compare-and-swap after the host read, done again from the new position if another thread moved it meanwhile (`libretro_vfs.cpp`) - so two threads reading one file on still each get a part of their own, and the position never passes the file's end. `test_vfs_positional` has four threads read one handle on at once, with a frontend that reads at offsets and with the two older kinds: every block is read by exactly one of them and the position ends at the end (fails on the position handled as it was). Writes, seeks and the rest still take the mount's lock. Not run with a game.
- A game's read at an offset (`cellFsReadWithOffset`, the third `std::shared_lock`) takes no lock. Every such read took its mount point's lock shared for as long as the host read took: all the files of the disc, or of the hard disk, on one word that each read wrote twice, and every read on a mount waited whenever anything on it was written, renamed or closed. A read is now counted on its own file (`lv2_file::io_begin`/`io_end`, two atomic adds on the file's line), and the one thing the lock was there for is kept another way: the host handle is taken away - by a close, or by a rename that has to close and reopen the file - only once no read is in flight, and no read begins while it is away. `test_vfs_positional` has three threads read while the handle is swapped under them 300 times (hangs or dies without the check for a handle that is away). Reads through the file's position (`sys_fs_read`) still take the mount's lock, exclusively: next. Not run with a game. Five `std::shared_lock`s are left.
- A game's file read or write into memory the emulator does not hand straight to the host (anything but the first 256 MB and the stack) went through a 64 KB `std::vector` that was allocated and zeroed for every call. The buffer is on the stack now: no allocation and no clearing on the way of a read. (The copy through it remains; reading straight into that memory is a separate question of which guest memory the host can be given.)
- Looking up an exported function takes no lock (`ppu_get_exported_func_addr`, the second `std::shared_lock`). It took the link tables' lock shared and went through two `std::map`s, the outer one keyed by the module's name. Every function's link entry is now also published, when it is made, in a map that only gains entries and is read with no lock (`Utilities/lf_u64_map.c`, C89), under a 64-bit key of the module's name and the function's id; the lookup is one hash and a few loads, and reads the address out of the entry as the word it is. The tables are still built under their lock. A key shared by two functions would hand one the other's address, so publishing checks it; `test_vfs_positional` holds all 3805 functions the emulator's own 153 modules register to it (none clash, and they use 3% of the map), and `test_lf_u64_map` covers the map itself, also under ThreadSanitizer. Not run with a game: a game's and the firmware's modules publish through the same four places. Six `std::shared_lock`s are left.
- An SPU function's module is hashed where it is written. To name the object a module compiles to, its bitcode went through `WriteBitcodeToFile`, which makes a 256 KB buffer of its own for every module, writes into that and copies the result into the caller's stream - here another buffer, made for each function too. The recompiler now writes with `BitcodeWriter` straight into one buffer of its own that keeps its room from one function to the next, and hashes it there; the string naming the CPU and LLVM is made once, not per function. Loading 200 functions from their objects takes 200 ms where it took 229 (`test_llvm_jit`). The objects' names change with this, so SPU objects kept by an earlier build are compiled once more.
- The first of the core's reader locks (`std::shared_lock`) is gone: the EEPROM bytes of `sys_ss`'s update manager. They were an `unordered_map` behind a reader-writer lock, taken shared for every read and exclusive, with a map node allocated, for every write. They are a fixed table of 64-bit words now (`Emu/Cell/lv2/eeprom_table.c`, C89): an offset and its byte in one word, found by hashing the offset, claimed and replaced with a compare-and-swap; a read is a few loads, a write allocates nothing, and nothing waits. `test_eeprom_table` (also under ThreadSanitizer) covers reads and writes, offsets that hash together, a full table, and four writers against six readers (fails when a writer does not recognise its own word). Seven `std::shared_lock`s are left.
- RPCS3's own engine for waiting on an atomic and waking it is gone: `atomic_t`'s `wait`, `notify_one` and `notify_all` go through libretro-common's new `retro_waitaddr` (over `retro_eventcount` and `retro_atomic`). `rpcs3/util/atomic.cpp` goes from 1414 lines to 181 - the hash table of 131072 entries (8 MB), the pool of condition handles, the per-platform sleeping (futex and futex_waitv, NtWaitForAlertByThreadId, keyed events, a mutex and condition variable elsewhere) are removed. A notify with nobody waiting - most of them: every thread state change, every lv2 object signalled - was a system call every time on Linux, 133 ns here; it is one read-modify-write now, 11 ns with the store. Windows searched its hash table there instead; that path is replaced by the same code and is not measured. A wait parks through one record of the waiting thread's, published under each address it names, on every platform, so waiting on several words no longer needs futex_waitv (Linux 5.16). First step of taking `atomic.hpp` out for `retro_atomic` used directly. `test_vfs_positional` wakes sleeping threads with `notify_all` and with `notify_one`, checks a bounded wait against its bound and the cost of a notify nobody hears (fails on the old engine's 133 ns); the whole of `make check`, which waits and wakes all through, passes on it. Not run with a game, and not on Windows.
- Two things every syscall and every call into an emulated library paid for a log are gone. Each syscall added one to a counter that all PPU threads share (the threads take the counter's cache line from one another on every call), for a thread that woke every second and wrote the counts into the log every ten: the counter and the thread are removed. And each syscall and library call wrote itself into its thread's call history - a division, to find the slot, and four stores - also when the history is not kept (the PPU call history setting, off), where it is one entry long and read by nothing: it is written only when it is kept. Two gates in the library tests.
- An error a game's call returns costs nothing when it is not logged. Games get errors back all the time - a lock that is taken, a wait that timed out, a file that is not there - and every one that is not marked as expected went through `error_code::error_report`: the function's name and the error were formatted into a string, the call's arguments after them, and the string was counted in a per-thread map of every such string the thread had ever made, to log each one only three times. All of that also with the log off, and the map only grew (152 bytes an error with a new argument in it). Now the report returns at once when its channel's level is not logged: 3.5 ns an error where it was 448 ns, and nothing kept (`test_vfs_positional`, 20000 errors with the log off; fails without the early return).
- A compiled shader goes to the Vulkan driver from where the compiler wrote it. `shader::compile` had the module copied out of the compiling thread's block into a vector of its own (an allocation and a copy for every shader, mid-game for a program a game brings up), handed that to `vkCreateShaderModule`, which keeps its own, and then kept the vector for the life of the shader with nothing ever reading it - beside the GLSL text, 20 to 50 KB a program, kept the same way. Now `spirv::compile_glsl_lent` lends the module in the thread's block until that thread compiles again, the driver is given those words, and the shader keeps neither them nor, once compiled, its text; the text is moved into the shader by the fragment and vertex programs, not copied; and a stage that comes as a built module is read where its owner has it. `test_shader_corpus` checks that every module the renderer compiled was lent from the thread's block and that the text is gone after the compile (fails when it is kept).
- The SPU recompiler's compiled code is kept between boots. Upstream compiles every SPU function again on every boot ("Building SPU cache"): it has an object cache for them, but only under the SPU debug option and marked testing only, because an object was named by its SPU code alone - with another setting, another CPU or another version of the recompiler the old object would have been loaded for a function that now compiles to something else. An object is now named by a hash of the LLVM module it is compiled from, as it stands before the passes, written out as bitcode, with the CPU and LLVM version: it is found only when it is that very module's, whatever the module was built from. When it is there, the passes, the verifier and code generation are not run - in `test_llvm_jit`, 200 functions of 40 to 400 instructions take 3.7 s to compile and 0.23 s to load from their objects on a later boot (code generation is 79% of a compile, the passes 14%). The objects go into one `llvm/objects.pack` beside the game's PPU cache and are lent to LLVM from it. Also gone from every compile: a disassembly listing of the function and a print of its whole module, both made for a debug file or a log that are not there (4% of a compile). `test_llvm_jit` checks that a second boot compiles nothing, in the opposite order too, and that a changed setting makes new objects where the old ones are not taken (fails when the name is made from the SPU code alone). Not run with a game.
- The on-disk shader cache is one file. It was a file for every pipeline and one for every fragment and vertex program - thousands for a game - each opened, read and closed when the game started, and when a new pipeline was made mid-game two files were looked for and up to three written. It is one `shaders.pack` now, the same pack the recompilers' objects are in: read once when the renderer starts, pipelines unpacked from that block, a fragment program's code lent from it where it lies (no buffer, no copy), and a new pipeline's three records written at the pack's end after a lookup in the index instead of on disk. A cache of files is moved into the pack the first time it is loaded and its pipeline files removed (the program files in `raw/` are left: other caches share them). For this the pack moved wholly into the C module (`Utilities/object_pack.c`: open, find, add, lend, read, each, over callbacks for the file), and the recompilers' cache uses that. `test_shader_corpus` stores pipelines, reads them back in the same session and a later one, checks that storing them again writes nothing and that the programs are lent, and moves a cache of files in (fails without the lookup before a write, and without the lend).
- `TTY.log` is gone. Every line a game printed to its TTY was written to that file as it came, on the game's own thread, on top of going to the log; and before that the text was copied out of the guest, searched for six words ("failed", "error", ...) to pick a log level, and now and then a dump of the thread's state was put together for a log message - all of it also when nothing was logged. What a game prints is in `rpcs3_detailed.log` (channel `TTY`) when the Detailed Log option is on; when it is off, `sys_tty_write` checks that the text is readable and does nothing else with it. A gate in the library tests keeps the file from coming back.
- A cache directory's compiled objects are one file, not a file each. Every part of a PPU module LLVM compiles was kept as its own object file, hundreds for a game with its firmware modules, and each boot opened and read every one of them twice: once only to see that it was there (`jit_compiler::check` loaded the whole object and threw it away), once to load it. They are now records in one `objects.pack` per directory (`Utilities/object_pack.c`, C89: the layout and a lock-free index). The pack is read once, whole, the first time its directory is asked for; an object in it is lent to LLVM from that block with no copy, and the block is freed when the last object lent from it is; `check` is a lookup in the index and reads nothing. A newly compiled object is written at the pack's end in place, straight from LLVM's buffer (`fs::file::write_at`, new: a write at an offset that leaves the handle's position alone, through the frontend's VFS v6 or `pwrite`), with no temporary file and rename. A record counts once its end mark is written, so a pack cut short by a crash counts up to there and is written on from there. Objects in files of their own, plain or `.gz`, are moved into the pack the first time they are loaded and their files removed. Nothing in it takes a lock. Measured here on Linux with the files already in the page cache, 600 objects of 150 KiB: 23 ms as files read twice, 20 ms as one pack, and 1200 opens become one; a cold disk and Windows, where an open costs far more, are not measured. `test_object_pack` (also under ThreadSanitizer) covers the layout, records cut short every way and the index from six threads; `test_llvm_jit` compiles into a pack, loads from it in the same session and a later one, moves loose and compressed objects in, and cuts a pack short and writes on (each shown to fail on a mutant).
- The emulator's logging is off unless asked for, and three costs of it are gone. Until now every message at RPCS3's default level was formatted on the thread that made it (two allocations a message), taken through one lock shared by all threads and kept in a list that only grew for as long as the core ran - standalone's `main()` tells the logger when it has started and the core never did - and then written to `rpcs3_detailed.log` and, deflated at the highest level on the log thread while the game ran, to a second copy, `rpcs3_detailed.log.gz`. Now the core says `logs::set_init`, so nothing is kept and nothing waits on that lock; the compressed copy is gone and what is waiting goes to the file in one write, not 32 KiB at a time; and a new core option, Detailed Log, off by default, decides whether there is a log at all. Off, `logs::set_ceiling(logs::level::fatal)` holds every channel at fatal errors - which is what puts "The emulation stopped: ..." on screen - so no other message is formatted or allocated for, and there is no log file, no writer thread and no 32 MB buffer for it. The option replaces Silence All Logs, which was off by default and silenced the on-screen error with the rest. For a bug report, turn Detailed Log on and send `system/rpcs3/rpcs3_detailed.log`. `test_vfs_positional` checks that nothing passes a channel under the ceiling, also after the emulator resets the levels as it does on boot (fails without the ceiling in `reset`), and that with the option the log is one complete plain file with no `.gz` beside it; two gates in the library tests keep the compressed copy and the missing `set_init` from coming back.
- Games start again on an NVIDIA GPU: every vertex program failed to compile there ("Failed to compile vertex shader", seen with Demon's Souls) since glslang was replaced. On an NVIDIA driver the vertex programs ask for an invariant position, and on a GPU with 64-bit floats they work the clipped depth out in doubles; rslc had neither, and `test_shader_corpus` never made either, because it built its programs only as the software driver it runs on gets them. rslc has both now (synced from RetroArch). The test builds every fragment and vertex program and the shader interpreter again as four other kinds of GPU get them - NVIDIA with doubles, a GPU without doubles or 24-bit depth, the low and ultra precision settings - 1812 sources where it had 572, and given a glslang it compares and runs all of them: 1005 fragment and 455 vertex stages make the same from both compilers. One thing is not as it was: on the low precision setting, half registers were native 16-bit floats on GPUs that have them; rslc has no 16-bit float type yet, so they are kept in floats and clamped, as on a GPU without them. Not run on a GPU here.
- The recompilers' cache is no longer compressed. Every PPU and SPU module LLVM compiles is kept as an object file so the next boot does not compile it again; those were stored gzip-compressed (`.obj.gz`), so every boot read each one, inflated it into a second buffer and copied that into a third for LLVM, and every first compile deflated it. They are stored as the objects they are and read once, straight into the buffer LLVM keeps. On 8.4 MB of object files (the core's own, standing in for a game's; from memory, the disk not counted): 1.1 ms to load where the compressed ones took 15 ms. A cache written before this still loads, and each of its objects is rewritten uncompressed the first time it is used, so it is inflated once more and never again. The cost is disk: the objects here are 4.6 times the size of their compressed form, and a slow hard disk reads that much more. `test_llvm_jit` compiles a module into a cache, checks the file is the object and not a compressed stream, runs it from there in a second compiler, and loads and converts a compressed one.
- The first shader stage that is built instead of written: the aggregator's compute task makes its stage by calls into rslc's builder, with no GLSL made, preprocessed or parsed. `spirv::build_begin` and `spirv::build_end` open and close a stage in the compiling thread's block, a shader takes a module as it is, and a compute task can hand one over in place of a source. The built module is word for word what the task's GLSL compiled to: `test_shader_corpus` keeps that GLSL and fails on any difference (it does with the atomic add built as another atomic), and the stage still goes through glslang's comparison and the run under it. On its own it is a small thing - 7 to 10 microseconds to build the stage where parsing it took 10 to 12 - and it is the pattern for the rest. rslc is synced with RetroArch's, whose builder gained the array length this stage needs.
- glslang is out of the core: the Vulkan renderer's shaders are compiled by libretro-common's rslc. `spirv::compile_glsl_to_spv` calls rslc where it called glslang, and glslang's submodule (58 MB of source), its 45 files in the build, its CMake and its start-up and shut-down calls are removed. Over the 572 shaders of `test_shader_corpus` rslc compiles in 116 ms what glslang took 1180 ms for, and a thread that compiles keeps one block for it - rslc's working state and the module it hands back - so a compile takes nothing from the heap after the thread's first, where glslang allocated all through. What the two were held to before the switch: the same interface and layouts on all 572, modules 0.07% larger, and the same output byte for byte from the 348 stages a software driver can run. `test_shader_corpus` now goes through the core's own compile and runs every stage it can; given a glslang executable in `SHADER_CORPUS_GLSLANG` it compares against glslang as before, and CI builds one outside the tree for that (that CI step is written and not run here). The test's runner is C89 now (`shader_runner.c`). Not shown by any of this: the 202 fragment stages built for the renderer's own interpolation with barycentric inputs, which is what a GPU that has them uses - they compile and match glslang's interface, and are not run, the software driver having no barycentric inputs; and nothing has been run with a game or on a GPU. The CMake lanes are configured and the changed files compiled, not built to the end.
- `test_shader_corpus` runs the vertex and compute stages too, and it found a shader rslc compiled wrong. A vertex stage is run from glslang's module and from rslc's for the same vertices with its position and every output captured by transform feedback; a compute stage runs one group and every buffer and image it can write is compared after. 99 vertex and 40 compute stages now make the same from both, with the 209 fragment stages. The one that did not: the aggregator's compute task adds up `src[i]` for `i < src.length()`, and rslc had compiled `length()` of an unsized buffer array as 0, so its module added nothing. That is fixed in RetroArch's rslc and synced here. The runner has a device of its own, with transform feedback. Not run: the 202 fragment stages built for barycentric inputs, the shader interpreter's 19 stages, 3 that read an attachment; a multisampled image a compute stage writes is not compared. With every fused multiply-add turned into a mix 90 of the 99 vertex stages put out something else; with every integer add turned into a subtract 12 of the 40 compute stages leave something else. glslang still compiles everything the core runs.
- `test_shader_corpus` runs the fragment stages, and rslc's draw what glslang's draw. For each stage the test reads the interface out of the module, gives every buffer, texture and push constant something to read (buffers filled member by member from the module's own types, three ways), writes a vertex stage that feeds every varying, and draws the same triangle with glslang's module and with rslc's into a target for each output, with depth and stencil. 209 stages run, and every byte drawn is the same. Not run: those 202 barycentric ones (the software driver here has no barycentric inputs), the shader interpreter's 16 (they run a program out of their buffers), 3 that read an attachment, and every vertex and compute stage. With every fused multiply-add in rslc's modules turned into a mix, 127 of the 209 draw something else, so the comparison sees the arithmetic. glslang still compiles everything the core runs.

- The plain-data queues are `retro_deque` too: RSX's frame-time and recovered-command histories, `sys_usbd`'s pending events, the Skylander, Infinity, Dimensions and Kamen Rider figures' statuses and replies, and a P2P stream socket's backlog were `std::queue` and `std::deque`, which take a block from the heap and give one back every few dozen elements for as long as they are used. - The lv2 event queues and the scheduler's lists are libretro-common's `retro_deque` (new there: a double-ended queue of one type in one block, C89), in place of the ring and the vectors that had replaced their `std::deque`s. - A thread going to sleep with a timeout, or waking from one, allocates nothing. The lv2 scheduler keeps the sleeping threads' deadlines in a list, the earliest first, and another list of threads about to sleep; both were `std::deque`, which takes a block from the heap and gives one back as its contents move along - every few dozen timed sleeps, under the scheduler's lock, all through play. A thread is in each list once at most, so room for as many as there can be threads (100 PPU and 1535 SPU) is set aside when the core is loaded - 26 KB for the deadlines, 13 KB for the other - and the lists never ask for more. - OpenGL: the renderer no longer draws into the texture the frontend is copying. There are now three textures, handed between the threads with one atomic exchange each and fenced on the GPU in both directions (`rpcs3/libretro/libretro_gl_frames.c`, C89, taking its GL functions from the caller). The renderer draws into one. retro_run copies the newest finished one once the GPU has drawn it. The renderer reuses a texture only once the GPU has finished the frontend's copy of it. - OpenGL: retro_run no longer waits on the CPU for the renderer's frame, and the renderer no longer checks and logs its framebuffer on every flip. Before blitting, retro_run used to wait up to 1 ms on the renderer's fence (`glClientWaitSync`), and past that blitted a frame the GPU had perhaps not finished. It now queues the wait on the GPU (`glWaitSync`), so the blit runs once the frame is drawn and retro_run never waits. On each of its several binds per flip, the renderer asked the driver for its framebuffer's status, which makes the driver validate it. Different from before: an MP3's length no longer counts its encoder padding (FFmpeg's estimate did); Vorbis, Opus and FLAC in Ogg have their tags listed (FFmpeg gave cellSearch none); the year of a date such as "2004-05-01" is listed, where only a bare year was. Not tried with a game yet.
- Video decoding for games (cellVdec: the movies and cutscenes in AVC, MPEG-2 and MPEG-4/DivX) goes through libretro-common's rh264, rmpeg1_video and rmpeg4_video instead of FFmpeg's decoders, and the pictures are converted for the game by libretro-common's YUV conversion instead of swscale. CI decodes streams FFmpeg encoded, with B pictures, and every picture is FFmpeg's - the same bytes in AVC, within one level in MPEG-2 and MPEG-4 - in display order, with the time stamps and user data of the access unit it came from and its picture type; B-skip and PB-skip drop the pictures they did; RGBA and ARGB come out within 3 levels of swscale's, UYVY the same. RGB is converted in the colour matrix the game asks for (BT.601 or BT.709), where swscale always used BT.601. MPEG-4's frame rate comes from the time between pictures, where FFmpeg's often fell back to 30. The decoded pictures go into buffers kept in a lock-free pool and reused, where a frame was allocated for every picture, and the alpha plane for RGBA output is gone. AVC decodes on one thread, about 80 pictures a second at 1080p on CI's machine. Not tried with a game yet.
- ATRAC3plus audio for games (cellAtracXdec: the music and voices of many PS3 games, and movie sound) is decoded by libretro-common's ratrac3p instead of FFmpeg's decoder. The sound is what it was: CI decodes streams of every channel configuration, mono to 7.1, with a different signal in each channel, and compares them with what the core's FFmpeg (8.1.1) path gave - within 7 millionths of full scale as floats, one step at 16 bits - with every channel in the place it was. A frame is decoded from where it lies in the game's memory, without copying it into the decoder's work memory first, and the decoder is made once for a stream and reset when the game starts it again, where FFmpeg's was set up again at every new sequence. Not tried with a game yet.
- Video post-processing for games (cellVpost: a decoded picture to RGBA for the screen) goes through libretro-common's YUV conversion and scaler instead of FFmpeg's swscale. The picture is converted in the colour matrix (BT.601 or BT.709) and range (full or broadcast) the game asks for, where swscale was always given BT.601 broadcast range. Scaled down, the picture is filtered with a windowed sinc instead of swscale's bilinear, which skipped samples: five times closer to a careful scaling of the same picture on CI's; scaled up it is bilinear, a little closer than before. The alpha the game asks for is put straight into each pixel, where a plane of it was allocated and filled for every picture, and a picture the size of the last takes no memory; one the size of the output is converted straight into the game's buffer. CI compares the conversion with what swscale wrote from the same picture (within 3 levels at one size, in both matrices) and the scaled pictures with a careful scaling of it, and counts the allocations of a repeated picture: none. Not tried with a game yet.
- The RSX blit engine's scaled and converting copies done in software (NV3089 with a scale, or between R5G6B5 and A8R8G8B8: some games' 2D blits, video and HUD layers) go through libretro-common's scaler instead of FFmpeg's swscale, the first of the core's uses of FFmpeg to move. Nearest-sample scaling picks the same samples as before; the "smooth" (first order hold) blits are now true bilinear, where swscale's fast bilinear stepped between columns. A8R8G8B8 to R5G6B5 takes each channel's top bits, where swscale went through YUV and shared colour between neighbouring pixels, which changed a noisy image's colours by up to half their range. The scaler and its buffers are kept from one copy to the next, so a copy the size of the last no longer sets up a new swscale context and allocates: it takes no memory. libretro-common is synced with RetroArch's. CI compares the copies with what swscale wrote from the same pixels (R5G6B5 to A8R8G8B8 the same bytes, nearest upscales the same colours, bilinear within 2 levels), checks every nearest pick and a short source slice, and counts the allocations of a repeated copy: none. Not tried with a game yet.
- JPEG headers for games (cellJpgDecReadHeader) are read right: the module walked a JPEG's segments by lengths read wrong (the high byte times 255, and from the second segment on the marker's own code in place of the length's low byte) and wanted a JFIF segment first, so it refused nearly every JPEG with CELL_JPGDEC_ERROR_HEADER - any with a quantization table before the frame header, which is how encoders write them, and every Exif file - and games could not decode them. Standalone RPCS3 has the same bug. The header is now found by the segments' real lengths, after any application segments (JFIF, Exif, Adobe), from any kind of frame (baseline, progressive, and the rest). CI reads the header of every test JPEG, with an Exif segment longer than 255 bytes, fill bytes and a progressive frame, and every file cut short before its frame header; the old walk refused all 16 test files. The component count and colour space reported stay as they were. Not tried with a game yet.
- Building the core needs no Vulkan or GLEW installed, with the Makefile or CMake, as libretro's other Vulkan cores build: Khronos' Vulkan headers (1.4.350), volk and GLEW (2.3.1) are in the tree (3rdparty/Vulkan-Headers, 3rdparty/volk, 3rdparty/glew). The core no longer links the Vulkan loader: volk loads Vulkan's functions when the core starts, from RetroArch's own `vkGetInstanceProcAddr` when RetroArch's context is Vulkan, else from the system's loader (vulkan-1.dll, libvulkan.so.1, MoltenVK) opened at run time - so the Windows core no longer imports vulkan-1.dll, the Linux core no longer needs libvulkan.so.1, and the macOS core no longer links MoltenVK. GLEW is compiled into the core on Linux and not used on Windows, where the OpenGL renderer loads its functions itself. The Makefile's checks for installed Vulkan and GLEW and its message about what to install are gone, as is the unused MoltenVK project. CI checks that the Linux and macOS cores need no Vulkan library and the Windows core imports no vulkan-1.dll. Not tried with a game yet.
- Makefile: a missing Vulkan or GLEW header or library stops `make` at once, saying which and what to install (in an MSYS2 shell, the pacman command for its packages), where the build ran until the first file that includes it (`vulkan/vulkan.h: No such file or directory`). On Windows, vulkan-1 is linked dynamically: MinGW has it as an import library only, which the core's static link passed over, so the link would have failed once the headers were there; a shared LLVM is linked the same way. The C files among RPCS3's sources are compiled with C flags, not C++'s (eight warnings each), and `ASMJIT_STATIC` is defined once (it warned "redefined" in every file using the JIT). The core's own warnings in libretro_core.cpp and libretro_input.cpp are fixed. CI checks that a missing header and a missing library each stop make with the message.
- JPEG decoding for games (cellJpgDec) writes each row straight into the game's buffer, in the format it asked for, instead of decoding the whole picture into memory of its own and copying it over, and takes its decoder from a pool of eight that finished decodes give back, instead of making one, with its planes and its picture, at every decode. Once the decoders have decoded an image of a size, decoding another no bigger takes no memory; the pool is lock-free and emptied when the emulation ends. Reading the header no longer copies the whole file into new memory first: a JPEG in the game's memory is read where it lies, a file into the pool's memory. A file cut short past its header is decoded as far as it goes, as standalone RPCS3's stb_image decodes it, where it was refused; a broken file leaves the rows decoded before the break in the game's buffer. CI decodes JPEGs in each layout and colour space games ask for and compares every byte with what the module wrote before, and counts the decoder's allocations: none after the first round, where the old way took five an image. Not tried with a game yet.
- Makefile: `make clean` run a second time no longer prints `make: [Makefile:...: clean] Error 1 (ignored)`. The folders it searches for objects include the generated sources' (rpcs3/libretro/generated/), which the first clean removed, and `find` failed on it; only folders that are there are searched now. CI cleans twice after the build and checks neither prints an error.
- Makefile: `make clean`, and the clean-up when the toolchain changes, delete only the build's own objects. They searched the whole tree for `*.o` and `*.d`, which in a checkout with the LLVM submodule found the files of those names that are test data in clang's tree (the fake toolchains in clang/test/Driver/Inputs) and deleted them; `git -C 3rdparty/llvm/llvm checkout -- .` puts them back. `make clean` no longer counts as a change of toolchain.
- The core is built as `parallel_ps3_libretro` (.so, .dll, .dylib) instead of `rpcs3_libretro`, with its own core info file, `parallel_ps3_libretro.info` (in libretro-super's dist/info, and its copy here in rpcs3/libretro/); `rpcs3_libretro.info` is left as it is. The buildbot's CORENAME, the CI scripts, the workflows' artifacts and the Makefile follow. The crash report is written as `parallel_ps3_libretro_crash.log`. The core still calls itself RPCS3 to the frontend (library_name), so the folders RetroArch keeps for it (configuration overrides, remaps, saves and states sorted by core) and the system/rpcs3/ directory stay where they are.
- CI checks in-memory save states: `make check` builds a program linked as the core is and has RPCS3's own serializer write a state into memory the way Save State does, compressed with zstd, and read it back the way Load State does, from the core's buffer through `make_savestate_reader`; a second state goes into the same buffer, which keeps its memory. The Makefile build workflow runs it.
- Makefile: an LLVM is used only when it is built for the system the core is for. In an MSYS2 shell, `/usr/bin/llvm-config` is MSYS's own LLVM, for its POSIX layer; the Makefile took it, and its headers (MSYS's `/usr/include`) against MinGW's broke the build at the first file (`conflicting declaration 'typedef struct _mbstate_t mbstate_t'`). It now looks for MinGW's under `$MINGW_PREFIX` first, and an `llvm-config` whose host is not the core's system - Windows (MinGW), Linux or macOS - is passed over with a message, or stops the build when HAVE_LLVM=1 asks for one.
- Windows (CMake build): the core no longer exports asmjit's and RtMidi's classes along with its libretro functions. Both are built into the core, not DLLs of their own, but asmjit's API was declared dllexport (its CMake variable ASMJIT_STATIC never reached the compiler) and RtMidi was built with RTMIDI_EXPORT; ASMJIT_STATIC is now defined for asmjit and the code that uses it, and RTMIDI_EXPORT is dropped, as the Makefile build has them. Seen on the Makefile's Windows build, where this took some 230 exports off the DLL; not tried on the CMake Windows build yet.
- Makefile, Windows (`platform=win`, MinGW-w64): the core it builds now loads. It needed MinGW's libstdc++-6.dll beside it (the link switched back to shared libraries before the C++ runtime came in), and exported some 230 of asmjit's and RtMidi's functions along with its own; it is now linked statically and exports its libretro functions and the NVIDIA/AMD GPU-selection flags only, and it links GLEW as the CMake build does on MinGW. RtMidi has its MIDI backend on Windows (WinMM) and macOS (CoreMIDI), as RtMidi's own build has by default, for Rock Band 3's MIDI instruments. Checked by building it with MinGW-w64 GCC 13 on Linux and loading it under Wine: it needs Windows' own DLLs, vulkan-1 and opengl32, nothing else. `libretro_vfs.cpp` includes `<sys/stat.h>` on Windows, which GCC's MinGW headers do not bring in by themselves.
- The core builds without CMake too: `make` at the top of the tree, as libretro's other cores build (Makefile, with the source lists in Makefile.common). It builds what the CMake build builds, from the same sources with the same flags: LLVM (21 or newer, found through llvm-config, linked statically), RPCS3's prebuilt ffmpeg (downloaded as the CMake build does, or `SYSTEM_FFMPEG=1`), GLEW statically; the config database, the overlays' icons, the VBlank list and RPCS3's game patches (fetched from rpcs3.net, `EMBED_PATCHES=0` to leave them out) are compiled in by a small C tool (rpcs3/libretro/make/embed.c) whose output is the CMake build's, byte for byte. The core exports its libretro functions and nothing else. `make check` loads it with every symbol resolved; CI builds it this way on Linux with LLVM 22. The macOS (`platform=osx`) and Windows (`platform=win`, MinGW-w64) sections follow the CMake build but have not been built yet.
- The Linux core no longer leaves a function of ffmpeg's undefined: the CMake build linked the prebuilt ffmpeg libraries with libavutil before libswscale, so `ff_init_half2float_tables`, which swscale calls and avutil has, was never taken in. The core loaded anyway, as RetroArch resolves functions when they are first called, and would have stopped at the first scaling that reached it; a loader that resolves everything at once (`RTLD_NOW`) refused it. avutil is now linked last.
- RPCN's messages (rooms, matchmaking, messages, scores, TUS) are read and written by the core's own code instead of the protobuf library, which is no longer built, nor is the Abseil library it fetched from GitHub at configure time (the protobuf submodule, `USE_SYSTEM_PROTOBUF` and the `protobuf_*` options of the CI scripts are gone). The code is made from RPCS3's `np2_structs.proto` by a script beside it (`rpcs3/Emu/NP/generated/np2_structs_gen.py`), with the names protobuf gave it, so RPCS3's code that fills and reads the messages is as it was. What goes to the server is the same, byte for byte, and what comes from it is read the same: CI reads 16,000 messages the protobuf library wrote, read in other ways it accepts, or broken, and every one must come out as protobuf made of it (RPCS3's own protobuf, at the commit it pinned, agreed with them all). A reply is read where it lies in the packet - its strings and bytes are not copied out - and a request is written straight into the packet that is sent, where it was written into a string, copied into a buffer and copied again. Not tried against the RPCN server yet.
- Text is drawn by libretro-common's rtt instead of stb_truetype, and stb is no longer in the tree (its submodule is gone): the overlays' text (the home menu, messages, trophies) and the fonts games draw with cellFont. Glyphs are placed exactly as before - CI packs whole pages of a TrueType and a CFF (CJK) font both ways and every glyph's place, size and advance is the same - and they come out closer to the true shape of the font: rtt follows curves more finely than stb did, about four times closer on average and three times in the worst texel, and still draws a page in about half the time. A font a game opens is kept in a table of the core's instead of in the game's memory after its CellFont, which stb's state overwrote; its glyphs are drawn straight into the game's surface instead of into a buffer allocated for each one and copied. Not tried with a game yet.
- Save states no longer go through a file: Save State has RPCS3 write the machine's state into memory the core keeps, and Load State boots from RetroArch's buffer through that same memory, instead of writing `<title>_libretro.SAVESTAT.zst` to disk and reading it back. A save copies the state once, into RetroArch's buffer; a load copies it once, out of it. The memory is kept for the session and reused by the next save, so it is not taken again each time. Not tried with a game yet.
- RPCN: dropping the connection (a failed login, a reconnect) no longer frees it under the reader and writer threads: it waits for both to have left it, which they do within 50 ms. Before, the connection could be freed while the reader was still in it. The two threads are told apart from it with atomics instead of a mutex each, and the packets to send go through a lock-free queue instead of a mutex-guarded list. The writer thread no longer ends for good after a failed send, which left later connections with nothing to send their packets. Not tried against the RPCN server yet.
- PNG decoding for games (cellPngDec) takes its decoder from a pool of eight that closed streams give back, instead of making one, with its 64 KB file buffer and its row memory, at every open and freeing it at every close. Games open PNGs as they load; once the decoders have decoded an image of a size, opening another takes no memory. The pool is lock-free and is emptied when the emulation ends. CI's PNG comparison now decodes all its 9440 cases with one decoder, reset in between, as the pool uses them.
- YAML goes through libretro-common's ryaml (reading) and ryaml_writer (writing) instead of yaml-cpp, which is no longer built (its submodule is gone): the configuration and per-game configurations, the patches and the patch configuration, games.yml, the disc image cache, the players' history, music playlists and the PRX validation files. A document is read where it lies - from the file's buffer, or from the string a setting comes in - instead of being copied into a tree of its own. The settings database (`config_database.dat`), which is JSON, is read with libretro-common's rjson in one pass that stops at the game's entry. Files written before read as they did: CI reads an excerpt of RPCS3's patch.yml (anchors and the `load` entries that name them, values on the line below their keys, escapes) and 300 documents written by yaml-cpp's emitter, and checks every tree against yaml-cpp's, then writes each again as the core now does and reads it back. What the core writes is laid out as before, two spaces a level; a double is written with the fewest digits that read back the same. Not tried with a game yet.
- RPCN's connection to its server is encrypted by libretro-common's own TLS client instead of wolfSSL, which is no longer built (its submodule and the `USE_SYSTEM_WOLFSSL` option are gone). RPCN reads on one thread and writes on another at the same time, which wolfSSL did through its "write dup"; libretro-common's client now has a duplex mode for this with no lock, where a key update the server asks for is answered by the writing side. The server's certificate is still not checked. The handshake waits on the socket for what it needs instead of spinning, for 10 seconds at most, and may now be TLS 1.3 where the server offers it. The error RPCN shows when this fails reads "TLS Error" instead of "WolfSSL Error". CI runs a reader and a writer thread on one connection against a local OpenSSL server, the way the RPCN client does, under AddressSanitizer and ThreadSanitizer. Not tried against the RPCN server yet.
- BC1, BC2 and BC3 (DXT) textures, for a GPU that cannot sample them itself (some phones), are decoded on the CPU by libretro-common's rdds block decoders instead of RPCS3's copy of bcdec, which is gone. The texels are the same (BGRA, straight into the upload buffer as before), except the interpolated alpha of BC3: bcdec cut each step of the ramp down, rdds rounds it to the nearest value, which raises it by one on about a quarter of those texels. A GPU that decodes BCn itself (most desktop ones) is not affected. CI checks the decoders against bcdec at the commit RPCS3's copy came from, over random blocks and every BC3 alpha ramp. Not tried with a game yet.
- SoundTouch is gone, and with it RPCS3's Time Stretching (Enable Time Stretching and its threshold, in the config and the home menu's audio settings). The core already kept it off: it only worked on top of cellAudio's own buffer, which the core also keeps off, and RetroArch's dynamic rate control keeps the sound in step with what it plays. The game's sound goes straight into the buffer RetroArch reads from, as it did. A config or database entry that still sets the two options is ignored.
- Save states. RetroArch's Save State and Load State now work, through RPCS3's own savestates: a save stops the emulation, writes the whole machine to a zstd-compressed state and boots back into it, which takes a few seconds and a few hundred MB; a load boots the state. The state is read from RPCS3's file straight into RetroArch's buffer. Its size is that of the state itself, which varies, not a fixed maximum. They are for saving and loading only: making one every frame is out of reach, so rewind, run-ahead and netplay stay off (the .info file says "basic"). Saving fails, as in RPCS3, while SPU threads cannot be paused where a state can be taken (SPU Savestates-Compatible Mode helps), while a video decoder is open or while the game is saving; RPCS3 says which on screen and the game carries on. Not tried with a game yet.
- HTTP goes through libretro-common's net_http instead of libcurl, which is no longer built (its submodule and the `USE_SYSTEM_CURL` option are gone): the clans server's requests, over https with libretro-common's own TLS client (no certificate checked, as before), and UPnP's. net_http keeps its connections and DNS cache for one thread, so every transfer runs on one network thread that callers hand their request to over a lock-free queue and wait on their own completion for; there is no lock. A clans request now gives up after 30 seconds instead of waiting for ever. The clan ticket and member data are base64-encoded with libretro-common's encoder instead of wolfSSL's (which stays, for RPCN). CI posts a clans request through net_http, built as the core builds it, to a server on the runner and checks the request and the answer, including an HTTP error page, which is still taken as the answer. Not tried against a clans server yet.
- JPEG and GIF decoding for games (cellJpgDec, cellGifDec) and the overlays' images (icons, backgrounds) go through libretro-common's rjpeg, rgif and rpng instead of stb_image, which is now built only for stb_truetype (the overlays' fonts). The game's buffer is decoded where it lies instead of being copied first, and the pixels go straight into the game's output buffer in the format it asked for, with no image-sized staging copy; a GIF is decoded in a single pass, and the decoder's memory and the read buffer for a file are taken once on each thread that decodes and kept. CI compares the three decoders with stb_image 2.30, the version RPCS3 pins, over PNGs, JPEGs and GIFs of every kind: the same pixels, except where stb_image was wrong - it swapped red and blue in a GIF's background colour, and in a 4:2:2 JPEG it weighed the last chroma column the wrong way round. RGB output from cellJpgDec was three-byte pixels cut from four-byte ones (scrambled); it is now RGB. A broken file is still refused with the same error, but may leave part of the output buffer written. Not tried with a game yet.
- PNG decoding for games (cellPngDec) goes through libretro-common's rpng_rows instead of libpng, which is no longer built. The pixel conversions games ask for (palette to RGB, transparency to alpha, adding, removing or moving alpha, 16 to 8 bits, RGB to gray) are done as the libpng the module used does them; CI compares the two byte for byte over every PNG colour type, bit depth and output format, interlaced or not, for both whole-image and row-by-row (progressive) decoding. A broken PNG now returns an error to the game instead of stopping the emulator. RGB-to-gray output of a PNG with colour chunks (gAMA, sRGB, cHRM, mDCV) comes out as libpng 1.6.59's did too, the version RPCS3 built: the channels weighted by the file's chromaticities, mixed in linear light when the file has a gamma, through the same tables, built once when the header is read. A row that needs no conversion is now handed on where the decoder left it instead of being copied first. Not tried with a game yet.
- UPnP port forwarding (Network > UPnP) goes through libretro-common's net_upnp instead of miniupnpc, which is no longer built. The router found before, saved in `upnp.yml`, is used again without a new search, and a port the router has taken is tried as the next one up, as before. Not tried with a real router by anyone yet.
- XML goes through libretro-common's rxml instead of pugixml: trophy configurations, the redump database check and the clans server's requests and responses. The trophy and redump files are read straight into the buffer the parser keeps, without the copy they went through before. Not tried against a clans server by anyone yet.
- RPCS3's own compression goes through libretro-common's Deflate instead of zlib: the compressed log (`rpcs3_detailed.log.gz`, still complete up to its last line after a crash), gzip savestates, IRD files, PKG/SDAT and SELF decompression and the IRD checksums. Savestates made before load as they did, and the ones the core writes are standard Zstandard frames, which the reference zstd reads (checked in CI). They come out a little larger: on one 16 MB sample 9% larger than zstd's, written at the same speed.

Takes effect when the game is started (NNshi).
- Frame Pacing is an option again (Emulator clock by default, or RetroArch: one PS3 refresh per frame RetroArch shows). It had been removed on one tester's result, which he could not repeat (NNshi).
- Pause and Frame Advance with the Vulkan renderer: once RetroArch stops asking for frames, the game waits after the frame it is drawing, and each Frame Advance step lets it draw exactly one frame and shows that one, drawn with the input of that step. The game used to run on for a tenth of a second and a step let 4-6 frames through (NNshi).
- Sound after unpausing: the first frames after a pause handed RetroArch up to four frames' worth of sound at once, which with RetroArch's audio sync on made the frame rate drop and swing for seconds. A pause is no longer made up for (NNshi).
- Linux: the core no longer links libGL, libGLX and libX11, so it loads on a system without X11. It links libOpenGL for OpenGL itself, and the GLX and Xlib functions it shares RetroArch's context with on an X11 session are found at run time, in RetroArch's own libraries.
- VBlank Frequency has a new choice, From List: a game named in `vblank_unlock.txt` runs with a 120 Hz VBlank - shown at 60 frames a second when it is a 30 fps game, at 120 when it is a 60 fps one - and any other game stays at 60 Hz. The list ships with the core and is written to `system/rpcs3/` when it is not there; the core never overwrites it, so titles can be added. It comes from the RPCS3 wiki's list of VBlank-compatible games and NNshi's testing.
- Frame Pacing is removed, option and code: the game's frames are timed by RPCS3's own clock, as in standalone. The other choice, one VBlank per frame RetroArch shows, added input lag and was better in no case tested.
- Save Data Slot is removed: the game's save list is always shown in the picture. The core picks the first entry itself only when the list cannot be shown.
- Default Resolution's tooltip warns against using it to upscale; Resolution Scale is for that.

## October 2026

### Upstream

- Merged up to upstream RPCS3 build 20243 (v0.0.43), after builds 20147 and 20149. The core reports upstream's version and build number, with this repository's commit after it, and logs both at start.

### Picture

- Vulkan through RetroArch's own hardware context: the renderer draws on RetroArch's device and hands each frame over as an image, with no copy through system memory. Finished frames are handed over in order, each once, so the picture no longer judders against RetroArch's refresh. The context is kept across RetroArch's video driver rebuilds, and replaced images stay alive until RetroArch has moved on.
- Before the first picture the Vulkan frame is 720p at the Resolution Scale, so the compilation progress is drawn sharp.
- A game no longer holds RetroArch through its PPU compilation at boot.
- Output Scaling and Vulkan Frame Readback are no longer options. Frame Pacing defaults to the emulator's clock.
- macOS: Vulkan through MoltenVK, no OpenGL in the core.

### Sound and pads

- Surround sound: the Audio Format option (Stereo by default, Surround 5.1, Surround 7.1) is what the PS3 reports to games, and with 5.1 or 7.1 the channels go to RetroArch's multi-channel output.
- Rumble through RetroArch's rumble interface.
- Pads report a PlayStation 3 controller, as standalone's handlers do, and the sticks reach full diagonals.

### Games and files

- PKG files are installed without being started, into the configured dev_hdd0, and the `.rap` licenses next to a PKG are installed with it.
- RPCS3's game patches (`patch.yml`) and its settings database ship with the core; Database Settings Override says whether the database's per-game settings apply. They, and the in-game overlays' icons, are rewritten when their contents differ.
- Save data is picked from the game's own list, shown in the picture.
- Emulate BD-ROM Read Speed as a core option.

### Core options

- The options carry RPCS3's own names and sections, in the layout NNshi proposed: CPU, GPU, Scheduling, Network, Debug, Core. Each option does what it says; several that were never read are now connected.
- Options for Disable Blit Engine Upscaling, RPCS3's performance overlay and the Resolution Scale Threshold.
- VBlank NTSC Fixup on by default, as in RPCS3.
- PSN Status says where an RPCN account comes from.
- On big.LITTLE ARM CPUs the compiler threads default to the big cores, and only the efficiency cores are left out.

### Builds

- macOS cores for Apple Silicon and Intel, and Android x86_64 next to arm64-v8a.
- The Windows core is `rpcs3_libretro.dll`; Linux links curl in instead of depending on Debian's libcurl-gnutls.
- Recipes for libretro's buildbot: Linux, Windows (cross-built with llvm-mingw), Android and macOS.
